Using servers from the terminal

The app lists its servers in the CLI options. Each one is connected at startup; a server that cannot be reached is retried every 30 seconds and its commands appear when it comes back. 

servers: [
    { name: 'node', url: 'http://localhost:8047' },
    { name: 'ops', url: 'https://ops.example.com', headers: { Authorization: 'Bearer ' + token } },
]

Every command of a server can be run two ways:

  • By name: echo hello. When several servers have the command, the default server runs it (server use <name>); without one you are asked which server to use.
  • With the server as prefix: node:echo hello always runs on that server. Use it when a local command has the same name (local commands win), or to pick a server explicitly.

A server command hidden by a local command (or a local alias) is reported once at startup (Server command "users" from "ops" is hidden by local "listusers"; use "ops:users".), listed by server info <name>, and noted in help of the local command.

CommandAliasesWhat it does
serverservers, srvOverview: every server with its status, URL, server and API version, number of commands and shell access
server listserver lsThe same table
server status [name]server ping, server infoWithout a name, pings every server at once and shows the round-trip time. With a name, shows that server in detail (versions, OS, shell, streaming) and, when it is unreachable, what to check
server commands [name]server cmdsThe commands each server provides, with the name to type: node:echo when a local command has the same name, ◆ when several servers share it
server reconnect [name]server rc, server connectConnect again and reload the commands. Without a name, the unreachable servers are retried; --all reconnects every server
server default [name]server useShow or set the default server, which runs commands several servers have and commands that need one server (server logs, scp). Remembered across reloads; --clear removes it

ssh [name] [command]shellInteractive shell on a server, or one command with its output (servers that enable the shell; see below)

Server names are not case-sensitive, a mistyped name gets a suggestion (Did you mean 'node'?), and help server <subcommand> shows each command with examples. Plugins add more: server logs (server-logs) and server jobs (server-jobs).

Connect your own server

Users can link their own Node, .NET or Python server from the terminal, in any app (the Android app, the docs site, a page that configures no servers). server add asks for the URL, checks that it is a Qodalis CLI server, then offers three ways to sign in:

  • Approve in the browser (recommended): the terminal prints a link to the server's page /qcli/admin/link?code=ABCD-2345 and opens it. Sign in there, check that the code matches and approve: the terminal receives an API token for your account and connects. Needs the users and admin plugins on the server (1.0.0-beta.25 or later).
  • Paste an API token created with token create <name> (hidden input), or server add home https://cli.example.com --token qcli_pat_… in scripts.
  • User and password: the terminal signs in once, creates an API token for this device and signs the session out.
server add                                # asks for everything
server add https://cli.example.com        # approve in the browser
server edit home --token                  # paste a new token
server remove home                        # unlink it and delete its token
server forget-all                         # unlink every linked server

Linked servers are kept across reloads and marked linked in server list. Their tokens are encrypted with a Web Crypto key that cannot be read out (IndexedDB), never shown again, never written to the command history and never put in WebSocket URLs. Only https servers can be linked; http is accepted for localhost and private addresses after a confirmation. Revoke a token on the server with token revoke: the terminal then says to link the server again.

Apps decide whether users may link servers with the userServers option: false turns it off, { allowedOrigins: ['https://*.example.com'] } accepts only matching servers. The app's own servers cannot be removed or replaced from the terminal. To keep tokens in the platform's secure storage (Android Keystore, Keychain, Electron safeStorage), provide ICliSecretStore_TOKEN.

When a server is unreachable

server status <name> lists what to check. The usual causes:

  • The server is not running, or the URL (port, http / https) is wrong.
  • The server does not allow the page's origin. Browsers block the requests (CORS): add the origin to the server's allowed origins (allowedOrigins / QCLI_ALLOWED_ORIGINS).
  • A VPN, proxy or firewall blocks the connection.

Fix it, then run server reconnect, or wait for the automatic retry.

Paging long results

A server command that lists records pages them, so a terminal never receives thousands of rows. Such commands accept --skip (default 0) and --take (default 50, at most 500), and the terminal shows which rows you see and how to go on: 

accounts list --take 20
...
Rows 1–20 of 236 · next: accounts list --take 20 --skip 20

Writing such a command: declare the parameters, read them and write the rows with the paged table writer.

// .NET (Qodalis.Cli.Abstractions.Helpers)
Parameters = CliPaging.Parameters();
var page = CliPaging.From(command);                       // page.Skip, page.Take
builder.WritePagedTable(["Id", "Name"], rows, page, total);
// Node
parameters = CliPaging.parameters();
const page = CliPaging.from(command);                     // page.skip, page.take
builder.writePagedTable(['Id', 'Name'], rows, page, { total });
# Python
parameters = CliPaging.parameters()
page = CliPaging.from_command(command)                   # page.skip, page.take
builder.write_paged_table(["Id", "Name"], rows, page, total=total)

Without a total, pass hasMore (query one row more than the page). On the wire the table carries page: { skip, take, total?, hasMore }.

As a safety net, a table from a command that does not page is cut at the server option maxTableRows (.NET MaxTableRows, Python max_table_rows; default 200, 0 = no limit) and the terminal says the rest was left out. Raise the limit only for commands you control; paging is the fix.

Help for server commands

Server commands can carry the same help as web commands. Every field is optional, and older servers send none of them. help <command> then shows the documentation and examples, and lists the allowed values of each parameter. Tab completes those values, and the terminal refuses others before sending. 

// Node
aliases = ['exp'];
module = 'orders';
icon = '📦';
documentation = 'Writes the orders of a day.\n\nLarge days are paged.';
examples = [{ command: 'export --format csv', description: "Today's orders as CSV" }];
parameters = [new CliCommandParameterDescriptor('format', 'Output format', false, 'string', ['f'], 'csv', ['csv', 'json'])];
// .NET
public override IEnumerable<string>? Aliases { get; set; } = ["exp"];
public override IEnumerable<CliCommandExample>? Examples { get; set; } = [new("export --format csv", "Today's orders as CSV")];
// in the parameter: AllowedValues = ["csv", "json"]
# Python
@property
def examples(self):
    return [CliCommandExample("export --format csv", "Today's orders as CSV")]
# in the parameter: allowed_values=["csv", "json"]

Aliases work on commands and sub-commands, and the server resolves them too. In the terminal, node:export also answers to node:exp, and the bare alias exp is added unless a local command owns that name. module and icon place the command in the help list. Help always names the server the command runs on.

Remote shell security

The ssh command opens a PTY shell on the server (/ws/v1/qcli/shell). That is OS-level access, so the shell is off by default and, once enabled, it is locked until you choose how callers are authorized. It works with and without the users module.

ModeWhenWho may open a shell
users The server's users plugin is mounted Signed-in users with the shell:execute permission (single-use WebSocket ticket)
token No users plugin, a shell token is configured Clients sending Authorization: Bearer <token> (configure it in the client's server headers)
custom No users plugin, an authorize callback is configured Whatever your callback allows (headers, query, remote address)
anonymous Only with an explicit allowAnonymous Anyone who can reach the server (logs a startup warning; development only)
locked Enabled, nothing of the above Nobody (startup error explains the options)

Server options (names per server):

// Node
createCliServer({ enableShell: true, shell: { token: process.env.QCLI_SHELL_TOKEN, maxSessionsPerUser: 3,
    idleTimeoutMs: 15 * 60_000, env: { allow: ['TZ'] } } });
# Python
CliServerOptions(enable_shell=True, shell=CliShellOptions(token=os.environ["QCLI_SHELL_TOKEN"], idle_timeout=900))
// .NET
cli.EnableShell(o => { o.Token = builder.Configuration["Shell:Token"]; o.IdleTimeout = TimeSpan.FromMinutes(15); });

Client side, token mode needs the header on the server entry and, because the shell socket reads the token from the URL, unsafeHeadersInWebSocketUrl (the token then shows in access and proxy logs; prefer users mode for anything beyond a private network): 

servers: [{ name: 'ops', url: 'https://ops.example.com', headers: { Authorization: 'Bearer ' + shellToken },
    unsafeHeadersInWebSocketUrl: true }]

In every mode:

  • Session-bound (users mode): logout, expiry, an administrator revoking the session, disabling the user or removing shell:execute closes open shells immediately.
  • Limits: sessions per user (default 3) and in total (20), idle timeout (15 min), optional maximum duration.
  • Minimal environment: the shell no longer inherits the server's environment (secrets); only PATH, HOME, USER, LANG, TERM, SHELL and the variables you allow.
  • Audit: shell_opened / shell_closed entries (users mode) with user, mode and duration, never the command text.
  • Client: with an auth module loaded, ssh itself requires shell:execute; rejections are shown as "login required", "permission denied", "shell timed out", "too many shell sessions" instead of a generic socket error.

Choosing a server from your own commands

Commands that talk to a server without the user naming one (for example server logs, data-explorer, scp) should not simply take the first configured server: it may be down, or protected by the users plugin while the user has not signed in to it. Use cliDefaultServer(context) from @qodalis/cli-core. It returns the default server (server default <name>) when connected, otherwise the first connected server, and falls back to the first configured server so the user still gets a clear error from it. 

import { cliDefaultServer, resolveServerHeaders } from '@qodalis/cli-core';

const server = cliDefaultServer(context);
if (!server) { context.writer.writeError('No server configured'); return; }
const headers = resolveServerHeaders(context.services, server.name, server.headers);
const res = await fetch(`${server.url}/api/v1/qcli/...`, { headers });

The same choice is available as ICliServerManager.preferredServer() (service ICliServerManager_TOKEN). Always pass requests through resolveServerHeaders so they carry the signed-in user's token on protected servers.

MCP endpoint

Every server (.NET, Node, Python) can expose the whole system to AI clients such as Claude Code through the Model Context Protocol: CLI commands, the filesystem API, the data explorer, jobs, and tools contributed by plugins. It is a feature of the core server, off by default, and works with or without the users plugin. Each tool runs with the same permissions the caller would have in the CLI.

The endpoint is POST /api/qcli/mcp: MCP "Streamable HTTP", stateless (no Mcp-Session-Id), JSON responses only. GET and DELETE return 405.

Enabling

// Node
createCliServer({ mcp: true });
createCliServer({ mcp: { tools: ['weather_*', 'fs_*'], exclude: ['fs_delete'], instructions: 'Ops server' } });
# Python
CliServerOptions(mcp=True)
// .NET
cli.AddMcp(o => { o.Exclude = ["fs_delete"]; });
OptionMeaning
toolsAllow-list of tool names; a trailing * matches a prefix (weather_*)
excludeDeny-list, same syntax, applied after tools
tokenStatic bearer token required by the endpoint; only used without the users plugin
instructionsText returned to the client by initialize

Each server's README has the exact option names under "MCP endpoint".

Tools

Tools are collected on every request, so newly registered commands, enabled features and permission changes show up immediately. A feature's tools exist only when that feature is enabled on the server, and they go through the same services and safety checks as its HTTP routes (filesystem path whitelist, data-explorer limits, job scheduler). tools/list only returns the tools the caller may use, and tools/call checks again.

ToolsAvailable whenPermissions (users plugin)
server_info (read-only) Always Any caller that reached the endpoint
One tool per command: weather, weather_current, … (command parameters become the input schema, plus value for commands that take one) Always commands:execute plus each command's requiredPermissions along the command path
fs_list, fs_stat, fs_read (read-only) Filesystem API enabled files:read
fs_write, fs_mkdir, fs_delete (destructive) Filesystem API enabled files:write
data_sources, data_schema (read-only), data_query Data explorer enabled data:query
jobs_list, jobs_get, jobs_history (read-only) Jobs plugin installed jobs:read
jobs_trigger, jobs_pause, jobs_resume, jobs_stop, jobs_cancel Jobs plugin installed jobs:manage
Plugin-contributed tools The plugin registers a tool provider The permissions the tool declares

The interactive shell is never a tool. Results come back as text (plus structuredContent when a tool returns a single JSON object); a failed command or service error sets isError. On a name collision, built-in feature tools win over command tools. Plugins and host applications add tools by registering a tool provider (Node server.mcp.addProvider(p), Python result.mcp.add_provider(p), .NET services.AddMcpToolProvider<T>()); each tool declares its name, description, input schema, required permissions and MCP annotations.

Authentication and security

  • With the users plugin: requests authenticate like any other server request, with a session or an API token (Authorization: Bearer qcli_pat_…). The endpoint requires commands:execute; each tool then checks its own permissions. Create tokens with the users plugin's token command; a token created with --permissions only sees what that scope (and the user's current permissions) allows. Revoking a token or disabling its user takes effect on the next request.
  • Without the users plugin: set the token option to require Authorization: Bearer <token>. Without it the endpoint is as open as /execute; only do that on a trusted network.
  • Browsers: a request carrying an Origin header must come from an allowed origin or the same origin (DNS-rebinding protection).

Using the MCP endpoint from Claude Code

Default ports: .NET 8046, Node 8047, Python 8048. The examples use Node.

  1. Enable MCP on the server (details in each server's README, "Using the MCP endpoint from an MCP client"):
    • .NET: cli.AddMcp() — cli-server-dotnet
    • Node: createCliServer({ mcp: true }) — cli-server-node
    • Python: CliServerOptions(mcp=True) — cli-server-python
  2. Get a token. With the users plugin, sign in to a CLI connected to the server (usersModule.configure({ server })) as the user Claude Code should act as, and create an API token. It (qcli_pat_…) is shown once, together with the Claude Code command: 
    token create claude --expires=90
    Without the users plugin, use the server's static token option instead.
  3. Connect Claude Code, either way:
    • Direct HTTP (nothing to install): 
      claude mcp add --transport http qcli http://localhost:8047/api/qcli/mcp --header "Authorization: Bearer <token>"
    • The @qodalis/mcp-cli package, a local stdio MCP server that proxies to the endpoint. It is configured with environment variables, can sign in with a user name and password instead of a token (and signs in again when the session expires), and adds a read-only mode and client-side tool filters: 
      claude mcp add qcli -e QCLI_URL=http://localhost:8047 -e QCLI_TOKEN=<token> -- npx -y @qodalis/mcp-cli
    Add --scope user to make the server available in every project, or --scope project to share it through the project's .mcp.json (keep the token out of it: use an environment variable reference such as ${QCLI_TOKEN}).
  4. Check the endpoint with curl: 
    curl -s http://localhost:8047/api/qcli/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer $QCLI_TOKEN" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

Troubleshooting: claude mcp list shows whether Claude Code can connect to qcli; inside a session, /mcp shows its status and tools (and lets you reconnect).

SymptomCause
401 / failed to connectToken missing, mistyped, expired or revoked (token list), or its user is disabled
403The request's Origin is not allowed (add it to the server's allowed origins), or the caller lacks commands:execute
A tool is missingThe feature is not enabled on the server, the caller (or the token's --permissions scope) lacks the tool's permissions, or the tools / exclude lists hide it
404 / 405MCP is not enabled on the server, or the URL is wrong (the endpoint only accepts POST)

Jobs that run elsewhere (.NET)

The jobs API, the jobs_* MCP tools, the server jobs commands and the dashboard's jobs page work on an ICliJobManager. The default one runs the jobs registered with AddJob in the server's process. When your jobs run somewhere else (a worker service, a queue, your own scheduler), implement ICliJobManager over them and register it; the CLI and the dashboard then list and control those jobs. 

cli.SetJobManager<MyJobManager>();   // scoped: it may use the request's services

public class MyJobManager : ICliJobManager
{
    public Task<IReadOnlyList<CliJobInfo>> GetJobsAsync(CancellationToken ct) => ...;   // Actions = ["trigger", "pause", "resume"]
    public Task TriggerAsync(string jobId, CancellationToken ct) => ...;
    public Task PauseAsync(string jobId, CancellationToken ct) => ...;
    public Task ResumeAsync(string jobId, CancellationToken ct) => ...;
    public Task<(IReadOnlyList<JobExecution> Items, int Total)> GetExecutionsAsync(string jobId, int limit, int offset, string? status, CancellationToken ct) => ...;
    public Task<JobExecution?> GetExecutionAsync(string jobId, string executionId, CancellationToken ct) => ...;
}

Stopping, cancelling and changing a job's options default to NotSupportedException, answered with 501 (NOT_SUPPORTED). Each job lists the actions it offers in actions, and the dashboard shows only those buttons. Throw KeyNotFoundException for an unknown job (404) and InvalidOperationException when the job's state refuses the action (409).

Color scheme

Every color in the dashboard is a token, so you can match it to your own design. Set the scheme in the admin plugin's options; the shape is the same on all three servers: a mode (dark, the default, light, or system to follow the browser) and color overrides for the dark and light schemes. Tokens you leave out keep their defaults. 

// Node
new CliAdminBuilder()
    .setTheme({
        mode: 'system',
        light: { primary: '#2a6bba', primaryHover: '#1f5596', accent: '#2a6bba', background: '#f1f6fa',
                 backgroundAccent: '#f1f6fa', surface: '#ffffff', border: '#d9e3ec', text: '#142231', muted: '#5d6f82' },
        dark: { primary: '#4f9be0', primaryHover: '#3f8ad3', onPrimary: '#0d1823', accent: '#4f9be0',
                background: '#0d1823', backgroundAccent: '#0d1823', surface: '#13212f', border: '#22364a',
                text: '#e6eef6', muted: '#93a6b9' },
    })
    .build({ registry, eventSocketManager, builder, executor });
// .NET
cli.AddAdmin(o =>
{
    o.Theme.Mode = AdminThemeMode.System;
    o.Theme.Light = new AdminThemeColors { Primary = "#2a6bba", Background = "#f1f6fa", Text = "#142231" };
    o.Theme.Dark = new AdminThemeColors { Primary = "#4f9be0", Background = "#0d1823", Surface = "#13212f" };
});
# Python (token keys camelCase or snake_case)
CliAdminBuilder().set_theme({
    "mode": "system",
    "light": {"primary": "#2a6bba", "background": "#f1f6fa", "text": "#142231"},
    "dark": {"primary": "#4f9be0", "background": "#0d1823", "surface": "#13212f"},
})

Values must be plain CSS colors: hex (#rgb, #rgba, #rrggbb, #rrggbbaa), a color function with numeric arguments (rgb(), hsl(), hwb(), lab(), lch(), oklab(), oklch()) or a named color. The server rejects anything else at startup (an unknown mode or token, var(), url(), ;…), so a theme cannot inject CSS.

The server publishes the validated scheme at GET /qcli/admin/theme.json (public, like the dashboard files, because the sign-in page uses it too), for example {"mode":"light","dark":{},"light":{"primary":"#2a6bba"}}. The dashboard loads it before its first render and sets each token as a CSS custom property (--qcli-primary, --qcli-primary-hover, …). The embedded terminal keeps the CLI's own terminal theme.

The defaults match the Qodalis CLI panel: its grays, indigo accent with the violet glow, and status colors in dark; the same palette for light backgrounds in light.

Name and icon

By default the dashboard is "Qodalis Cli Admin" with the Qodalis Solutions logo. An application that ships it under its own name sets the admin plugin's branding: the name and icon of the browser tab, the sidebar and the sign-in page, and the name its terminal shows in the welcome banner. Anything left out keeps the default. 

// .NET
cli.AddAdmin(o => { o.Branding.Name = "RateBell"; o.Branding.IconUrl = "/favicon.svg"; o.Branding.CliName = "RateBell CLI"; });
// Node
new CliAdminBuilder().setBranding({ name: 'RateBell', iconUrl: '/favicon.svg', cliName: 'RateBell CLI' });
# Python
CliAdminBuilder().set_branding({"name": "RateBell", "icon_url": "/favicon.svg", "cli_name": "RateBell CLI"})

The icon is an absolute http(s) URL, a root-relative path or a base64 data:image URL; the servers validate the values at startup and publish them as branding in /qcli/admin/theme.json. The terminal's copyright line, documentation link and version stay Qodalis CLI's (version adds the name). In a web app, the same name and icon go in the CLI's branding option.

The terminal's user

On a server with the users plugin, the dashboard's terminal is signed in as the dashboard's user: its prompt, whoami, id and perms show that user, and logout signs out of the dashboard. Without the users plugin (static admin password) the terminal only sends the dashboard's token with its requests.
