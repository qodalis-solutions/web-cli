Each method writes a message with a colored prefix icon.

writeInfo(message)Blue ℹInformational messages

Color Wrapping

Wrap text in ANSI color codes. Returns the wrapped string (does not write to terminal).

MethodParametersDescription

HTTP Client

The ICliHttpClient interface provides typed HTTP methods with automatic abort signal integration. When the user presses Ctrl+C, in-flight requests are automatically cancelled. Access it via context.http.

Methods

MethodSignatureDescription
get get<T>(url, options?): Promise<T> GET request, returns parsed JSON
post post<T>(url, body?, options?): Promise<T> POST request, auto-serializes body as JSON
put put<T>(url, body?, options?): Promise<T> PUT request, auto-serializes body as JSON
patch patch<T>(url, body?, options?): Promise<T> PATCH request, auto-serializes body as JSON
delete delete<T>(url, options?): Promise<T> DELETE request, returns parsed JSON
head head(url, options?): Promise<Response> HEAD request, returns raw Response
options options<T>(url, options?): Promise<T> OPTIONS request
fetch fetch(url, init?): Promise<Response> Raw fetch for streaming, headers, or status inspection

Request Options

All convenience methods accept CliHttpRequestOptions:

OptionTypeDescription
timeout number Request timeout in milliseconds. Automatically aborts the request after this duration.
headers HeadersInit Custom request headers
signal AbortSignal Additional abort signal (merged with the command's signal)

Examples

// Typed GET request
const users = await context.http.get<User[]>('https://api.example.com/users');

// POST with auto-serialized JSON body
const result = await context.http.post<Todo>(
    'https://api.example.com/todos',
    { title: 'New task', completed: false },
);

// Request with timeout
const data = await context.http.get('https://api.example.com/slow', {
    timeout: 5000, // abort after 5 seconds
});

// Raw fetch for streaming
const response = await context.http.fetch('https://example.com/large-file');
const reader = response.body?.getReader();

// Error handling with abort detection
try {
    const data = await context.http.get(url);
    context.writer.writeJson(data);
} catch (error: any) {
    if (error.name === 'AbortError') {
        context.writer.writeWarning('Request cancelled.');
    } else {
        context.writer.writeError(error.message);
    }
}

Auto-Abort Behavior

The HTTP client automatically merges the command's AbortSignal. When the user presses Ctrl+C, all pending requests from the current command are cancelled immediately. The fetch call rejects with an AbortError.

If you provide a timeout, a separate AbortSignal is created and merged with the command signal — whichever fires first wins.

State Management

The ICliStateStore provides reactive, persistent state scoped to each command processor. State is automatically persisted to localStorage and restored on boot. Access it via context.state.

Declaring State

Define initial state on your command processor using stateConfiguration:

const myProcessor: ICliCommandProcessor = {
    command: 'counter',
    description: 'Persistent counter',
    stateConfiguration: {
        initialState: { count: 0, lastAction: 'none' },
        storeName: 'my-counter', // optional custom key (defaults to command name)
    },
    // ...
};

async processCommand(command, context) {
    const state = context.state.getState<{ count: number }>();

    // Read
    context.writer.writeInfo('Current count: ' + state.count);

    context.state.updateState({ count: state.count + 1 });

    // Reset
    // context.state.reset();
}

    console.log('State updated:', state);
});

Command Guards

A command guard is a global check that runs before every command, across all processors and modules, and can block it. Use guards for cross-cutting policies such as authentication, permission checks, feature flags, maintenance windows or rate limiting, instead of repeating the check in each processor.

Guards are opt-in. With no guard registered every command runs as before. Guards differ from processor hooks: hooks belong to a single processor, while guards are registered once and apply to every command.

The ICliCommandGuard Interface

interface ICliCommandGuard {
    /** Unique name, shown in diagnostics when the guard throws */
    name: string;

    /** Execution order; lower runs first. Defaults to 0 */
    priority?: number;

    /** Optional filter: return false to skip this guard for the command */
    appliesTo?(
        processor: ICliCommandProcessor,
        command: CliProcessCommand,
        context: ICliExecutionContext,
    ): boolean | Promise<boolean>;

    /** Decide whether the command may run */
    canActivate(
        command: CliProcessCommand,
        processor: ICliCommandProcessor,
        context: ICliExecutionContext,
    ): CliCommandGuardResult | Promise<CliCommandGuardResult>;
}

const ICliCommandGuard_TOKEN = 'cli-command-guard';

Return Values

canActivate returnsEffect
true or nothingThe command is allowed; the next guard runs
falseBlocked with <command>: permission denied
a non-empty stringBlocked; the string is printed as the error
{ allowed, message }Explicit form; message is printed when allowed is false
throws / rejectsBlocked with <command>: blocked by guard '<name>' (<error>) (fails closed)

A blocked command prints the message as an error and exits with code -1.

Execution Order

  1. The input is parsed and the processor (or sub-processor) is resolved.
  2. Global parameters such as --help are handled. Help is never guarded.
  3. The positional value is extracted into command.value.
  4. Guards run, sorted by ascending priority. For each guard, appliesTo is evaluated first (if defined), then canActivate. The first guard that blocks stops the chain.
  5. Required values and parameters are validated, processor hooks run, then processCommand.

Accessing the Context

Both appliesTo and canActivate receive the execution context of the command about to run. A guard can use it to decide what should be guarded and whether it may run:

  • context.services.get(token) / getRequired(token) resolve any registered service, for example a policy, permission or feature-flag service from another module.
  • context.userSession gives the signed-in user and their groups, when a users module is loaded.
  • processor.metadata carries declarative flags such as requireAuth and requiredGroups.
  • command.value and command.args hold the parsed input.
  • context.reader can prompt the user, e.g. for a confirmation guard.

Return a message to report a denial rather than writing to the terminal yourself, so output stays consistent.

Registering Guards from a Module

Add guards to a module's guards array. When the module boots, each guard is registered as a multi-provider under ICliCommandGuard_TOKEN. Several modules can contribute guards and all of them run. 

import { ICliCommandGuard, ICliModule } from '@qodalis/cli-core';

const maintenanceGuard: ICliCommandGuard = {
    name: 'maintenance',
    priority: -50,
    appliesTo: (processor) => processor.metadata?.module === 'billing',
    canActivate: (_command, processor, context) => {
        const status = context.services.get<MaintenanceStatus>(MaintenanceStatus_TOKEN);
        return status?.active
            ? `${processor.command}: billing is in maintenance until ${status.until}`
            : true;
    },
};

export const billingModule: ICliModule = {
    apiVersion: 2,
    name: 'billing',
    processors: [new InvoiceProcessor()],
    services: [{ provide: MaintenanceStatus_TOKEN, useValue: { active: false } }],
    guards: [maintenanceGuard],
};

Guards can also be registered at runtime, for example from a module's onInit:

context.services.set({ provide: ICliCommandGuard_TOKEN, useValue: myGuard, multi: true });

Example: Policy Resolved from a Service

The guard below asks a service which commands are behind a feature flag, and whether the current user may use them.

const featureFlagGuard: ICliCommandGuard = {
    name: 'feature-flags',
    appliesTo: (processor, _command, context) =>
        context.services.get<FeatureFlags>(FeatureFlags_TOKEN)?.isFlagged(processor.command) ?? false,
    canActivate: async (_command, processor, context) => {
        const flags = context.services.getRequired<FeatureFlags>(FeatureFlags_TOKEN);
        const enabled = await flags.isEnabled(processor.command, context.userSession?.user);
        return enabled ? true : `${processor.command}: not available for your account`;
    },
};

Authentication and Permissions

Processors can declare access requirements in their metadata. The core treats these flags as informational; a module that registers guards enforces them. 

const deployProcessor: ICliCommandProcessor = {
    command: 'deploy',
    description: 'Deploy the app',
    metadata: {
        requireAuth: true,          // must be signed in
        requiredGroups: ['ops'],    // and a member of at least one of these groups
    },
    async processCommand(command, context) { /* ... */ },
};
SetupBehaviour of requireAuth / requiredGroups
No users moduleIgnored; every command runs
@qodalis/cli-users (local or server mode)Enforced by the users:require-auth and users:required-groups guards, for processors from any module
Your own auth moduleEnforced by whatever guards your module contributes

Client-side guards improve the experience but are not a security boundary. When commands call a server, the server must still authorize each request.
