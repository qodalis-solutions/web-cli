Command Line

The terminal reads a line the way a Unix shell does: words separated by spaces, quotes to keep spaces in a word, flags, pipes, redirects, variables and wildcards. The rules below apply to every command, built-in or from a plugin.

Words and Quotes

Spaces separate the arguments. Double or single quotes keep a word with spaces together, and anything inside them is text, flags included. 

cat "my notes.txt"            # one argument: my notes.txt
grep "two words" notes.txt     # the pattern is: two words
echo "a --b"                   # prints a --b (no flag b)
echo "a" "b"                   # prints a b
echo it's fine                 # a quote without a pair is text

A value given after a flag loses its quotes: find --name "my file.txt" searches for my file.txt.

Flags

FormExampleMeaning
Long--lines 5, --lines=5A value after a space or =
Short-n 5, -n5The value can follow the letter directly
Combinedrm -rf dir, ls -laSeveral short on/off flags in one; the last may take a value (-rn 5)
Boolean--force, --force=falseOn when present
Lone dashpaste - b.txtAn argument (piped input), not a flag

Letters are combined only when each one is a flag of the command, so a command's own multi-letter flags keep working.

Pipes and Redirects

| passes a command's output to the next one; only the last command's output is shown. Errors and warnings of every command are shown. Output written as a table or list reaches the next command as text lines, structured output (JSON) as data. 

cat app.log | grep error | wc -l
server list | grep node
echo hello > greeting.txt     # write (replace) a file, nothing is shown
echo again >> greeting.txt    # add to the end
build 2> errors.txt           # errors to a file (2>> to add)

Redirects write whole lines and need the files plugin (@qodalis/cli-files). The target can be quoted: > "my dir/out.txt".

Running Several Commands

OperatorRuns the next command
a && bOnly if a succeeded
a || bOnly if a failed
a ; bAlways

Variables

NAME=value (or export NAME=value) sets a variable, env lists them. $NAME and ${NAME} are replaced by their value, $? by the exit code of the last command, and a leading ~ by the home directory. Inside single quotes nothing is replaced; inside double quotes it is. 

GREETING=Hello
echo "$GREETING, world"     # Hello, world
echo '$GREETING'            # $GREETING
cat ~/notes.txt

Wildcards

With the files plugin, unquoted arguments with *, ? or [...] become the matching paths, sorted. Names starting with . match only a pattern that starts with .; a pattern that matches nothing is passed as typed; a quoted pattern is never expanded. 

rm *.log               # every .log file here
cat docs/*.md          # in a folder
ls file?.txt [ab]*     # one character, or names starting with a or b
ls */                  # folders only
grep "*" notes.txt     # quoted: the text *

Tab Completion

Tab completes commands, sub-commands, flags and, with the files plugin, paths. Names with spaces are completed in quotes (cat my + Tab gives cat "my notes.txt"), also inside a quote you started. Press Tab twice to list the choices.

Writer API

The ICliTerminalWriter interface provides 16 methods for rich terminal output. Access it via context.writer in any command processor.

Basic Output

Method Description
write(text) Write text without a trailing newline
writeln(text?) Write text followed by a newline (empty line if no argument)

Styled Messages

Each method writes a message with a colored prefix icon.

Method Style Description
writeSuccess(message) Green ✓ Success messages
writeInfo(message) Blue ℹ Informational messages
writeWarning(message) Yellow ⚠ Warning messages
writeError(message) Red ✗ Error messages

Color Wrapping

Wrap text in ANSI color codes. Returns the wrapped string (does not write to terminal).

Method Parameters Description
wrapInColor(text, color) text: string, color: CliForegroundColor Wrap text in a foreground color (Red, Green, Yellow, Blue, Magenta, Cyan, White, Black)
wrapInBackgroundColor(text, color) text: string, color: CliBackgroundColor Wrap text in a background color 
const colored = writer.wrapInColor('Hello', CliForegroundColor.Cyan);
      writer.writeln(colored);

Data Display

Method Parameters Description
writeJson(json) json: any Pretty-print a JSON object with syntax highlighting
writeTable(headers, rows, options?) headers: string[], rows: string[][], options?: { fullWidth?: boolean } Render a formatted table. Set fullWidth: true to expand columns to terminal width.
writeObjectsAsTable(objects) objects: any[] Auto-infer columns from object keys and render as a table 
// Table with headers and rows
        writer.writeTable(
        ['Name', 'Role', 'Status'],
        [
        ['Alice', 'Admin', 'Active'],
        ['Bob', 'User', 'Inactive'],
        ],
        { fullWidth: true },
        );
        // Auto-table from object array
        writer.writeObjectsAsTable([

Auto-Abort Behavior

The HTTP client automatically merges the command's AbortSignal. When the user presses Ctrl+C, all pending requests from the current command are cancelled immediately. The fetch call rejects with an AbortError.

State Management

The ICliStateStore holds reactive state scoped to each command processor, saved in the browser (IndexedDB) and restored the next time the terminal starts. Access it with context.state.

Declaring State

Define initial state on your command processor using stateConfiguration: 

const myProcessor: ICliCommandProcessor = {
    command: 'counter',
    description: 'Persistent counter',
    stateConfiguration: {
        initialState: { count: 0, lastAction: 'none' },
        storeName: 'my-counter', // optional (defaults to the command name)
        autoPersist: true,       // save after every change
    },
    // ...
};
Option Default Description
initialState (required) The state before anything is saved. Saved state is merged over it, so keys you add in a later version are present for existing users.
storeName command name Key of the store; commands using the same name share it.
autoPersist false Save after every change (changes made in the same tick are saved together). Without it, call persist().
scope 'global' 'global': saved and shared by every terminal and tab of the browser. 'user': saved separately for each signed-in user (shared while nobody is signed in), and switched when the user changes. 'session': this terminal only, in memory, never saved.
syncAcrossTabs true Apply changes saved by other tabs and terminals right away.
version, migrate — Convert saved state when its shape changes (see below).

State Store API

Method Signature Description
getState() getState<T>(): T A shallow copy of the current state. Change state with updateState, not by mutating the result.
updateState(partial) updateState(Partial<CliState>): void Shallow-merge new values (only the provided keys change) and notify subscribers. Saved with persist(), or automatically with autoPersist.
update(change) update((state) => Partial<CliState>): Promise<void> Read, change and save in one step, under the cross-tab lock: change receives the latest saved state, so two terminals changing the same key (adding to one list) both keep their change.
select(selector) select<K>((state) => K): Observable<K> Reactive slice — emits only when the selected value changes
subscribe(callback) subscribe((state) => void): Subscription Listen to all state changes
reset() reset(): void Restore state to initialState
persist() persist(): Promise<void> Save the state (does nothing when no storage is available)
initialize() initialize(): Promise<void> Load the saved state, once. Done for you before the command first runs; later calls keep the changes made since.
reload() reload(): Promise<void> Read the saved state again, replacing the current state

Example: Counter with Persistent State

async processCommand(command, context) {
    const state = context.state.getState<{ count: number }>();
    context.writer.writeInfo('Current count: ' + state.count);

    context.state.updateState({ count: state.count + 1 });
    await context.state.persist(); // not needed with autoPersist
}

Several Terminals and Tabs

A global store has one saved state for the whole browser: every terminal (panel tabs, split panes) and every browser tab reads and writes the same data. Saving is safe when several of them change it:

  • A save writes the top-level keys this terminal changed, merged into what is saved, under a lock shared by all tabs. Two terminals changing different keys never overwrite each other.
  • Other terminals apply the saved change right away, so the next change they make starts from it. Keys they changed and have not saved yet are kept.
  • For the same key, the last persist() wins. To change a value based on what it is now (append to a list, increment a counter), use update(): it reads the latest saved state under the lock, so no terminal's change is lost. 
// Two tabs adding a todo at the same time both keep theirs
await context.state.update((state) => ({
    todos: [...state['todos'], { id: Date.now(), text }],
}));

State that only makes sense for one terminal (a cursor, a game in progress) belongs in a scope: 'session' store: it is never saved or shared. Personal data (preferences, notes) can use scope: 'user': with the users plugin, each user signed in to the terminal gets their own saved state, loaded when they sign in.

Migrating Saved State

When the shape of your state changes, raise version and convert older saved state in migrate. Saved state without a version counts as version 0. The converted state is saved again. 

stateConfiguration: {
    initialState: { todos: [] },
    version: 1,
    migrate: (state, fromVersion) =>
        fromVersion < 1
            ? { todos: state.items.map((text) => ({ text, done: false })) }
            : state,
}

Reactive Subscriptions

// Watch a specific slice of state
context.state.select(state => state.count).subscribe(count => {
    console.log('Count changed:', count);
});
// Watch all state changes
context.state.subscribe(state => {
    console.log('State updated:', state);
});

Services (DI)

Each terminal has a service container where the CLI and its modules register services by token and look them up with context.services. Modules declare services in services; they can also register them at runtime with context.services.set().

Typed Tokens

Create tokens with createCliToken, so lookups are typed without a type argument. At runtime a token is its string, and plain string tokens keep working. 

export interface ITodoStore { list(): string[] }
export const ITodoStore_TOKEN = createCliToken<ITodoStore>('todo-store');

const myModule: ICliModule = {
    apiVersion: 2,
    name: 'todo',
    services: [
        { provide: ITodoStore_TOKEN, useClass: TodoStore, deps: [ICliHttpClient_TOKEN] },
    ],
    async onInit(context) {
        const store = context.services.getRequired(ITodoStore_TOKEN); // ITodoStore
    },
};

The built-in tokens (ICliEventBus_TOKEN, ICliKeyValueStore_TOKEN, ICliAuthorizationService_TOKEN, …) are typed, and so are the tokens plugins export, such as IFileSystemService_TOKEN (files), IScpTransferService_TOKEN (scp) and CliApiTokensService_TOKEN (users).

Providers

Provider Description
useValue Register an existing value
useClass / useFactory + deps Created on the first get, with deps resolved then: dependencies only have to be registered by the time the service is used. Dependency cycles are reported.
multi: true Collect several providers; getAll(token) returns all
transient: true Create a new instance on every get
sealed: true The token cannot be overridden or removed

Overriding and Removing

Registering a token again overrides it. remove(token, provider) removes one registration, making the previous one active again; remove(token) removes them all. 

const mine = { provide: ICliHttpClient_TOKEN, useValue: tracingClient };
context.services.set(mine);
// ...
context.services.remove?.(ICliHttpClient_TOKEN, mine); // the default client is back

Lifecycle

  • When a module is unloaded (pkg remove, or before pkg update loads the new version), its commands, guards and permissions are removed, its onDestroy runs, and then the services it declared are removed. Services a module registers itself at runtime should be removed in its onDestroy.
  • When the terminal is destroyed, services the container created (useClass / useFactory) that have a dispose() method are disposed. Values registered with useValue belong to whoever registered them.

Event Bus

Every terminal has an event bus where the system, modules and commands publish and subscribe to events. Use it to react to something happening elsewhere (a package installed, a server connecting, a user signing in) without depending on the code that does it. Access it with context.events, or from the service container with ICliEventBus_TOKEN.

Subscribing

on(pattern, handler) returns a function that unsubscribes. A pattern is an exact type, a namespace wildcard such as package:*, or * for every event. 

const myModule: ICliModule = {
  apiVersion: 2,
  name: 'my-plugin',
  async onInit(context) {
    // Typed: the payload type comes from CliEventMap
    context.events?.on('package:installed', (e) =>
      context.writer.writeInfo(`Installed ${e.data.name}@${e.data.version}`));

    // A whole namespace; the payload is unknown
    context.events?.on('server:*', (e) => console.log(e.type, e.data));

    // Only the next one
    context.events?.once('boot:completed', (e) =>
      console.log(`Booted in ${e.data.durationMs} ms`));
  },
};

Handlers run synchronously in the order they subscribed. A handler that throws is logged and does not affect other handlers or the code that emitted the event. events$(pattern) returns the same events as an RxJS observable.

Emitting your own events

Name events namespace:name, using your plugin name as the namespace. Declare their payloads once with declaration merging, so emitters and listeners are type-checked: 

declare module '@qodalis/cli-core' {
  interface CliEventMap {
    'todo:added': { id: number; text: string };
  }
}

context.events?.emit('todo:added', { id: 1, text: 'Buy milk' }, { source: 'todo' });
context.events?.on('todo:added', (e) => e.data.text); // typed

Without a declaration, pass the payload type explicitly, or leave it out: 

context.events?.on<{ id: number }>('todo:done', (e) => e.data.id);
context.events?.emit('todo:refresh');

module:loaded / module:unloadedname, version, commandsA plugin was booted or unloaded

server:eventserver, type, dataAn event pushed by a server over its event socket

service:eventservice, type, dataA custom event from a background service (context.emit)

History and persistence

Events live in memory: each terminal has its own bus for its lifetime, and nothing is written to storage. Events describe something that just happened; replaying them after a reload would make plugins react twice. Data that must survive a reload belongs in a state store. The bus keeps the last 200 events, available with history(pattern?, limit?), for example to catch up on what happened before a plugin loaded.

The events command

Command Description
events watch [pattern]Print events as they happen, until Ctrl+C
events log [pattern] [-n N]Show recent events
events emit <type> [json]Emit an event, e.g. to test a plugin (needs system:events when the users plugin is loaded)

When to use it

  • React to the system: refresh a view when a server reconnects, update a cache after pkg update.
  • Let plugins cooperate without importing each other: one emits todo:added, another listens.
  • Keep using a direct call when one piece of code needs an answer from another; events are fire-and-forget notifications.

Command Guards

A command guard is a global check that runs before every command, across all processors and modules, and can block it. Use guards for cross-cutting policies such as authentication, permission checks, feature flags, maintenance windows or rate limiting, instead of repeating the check in each processor.

Guards are opt-in. With no guard registered every command runs as before. Guards differ from processor hooks: hooks belong to a single processor, while guards are registered once and apply to every command.

The ICliCommandGuard Interface

interface ICliCommandGuard {
        /** Unique name, shown in diagnostics when the guard throws */
        name: string;
        /** Execution order; lower runs first. Defaults to 0 */
        priority?: number;
        /** Optional filter: return false to skip this guard for the command */
        appliesTo?(
        processor: ICliCommandProcessor,
        command: CliProcessCommand,
        context: ICliExecutionContext,
        ): boolean | Promise<boolean>;
        /** Decide whether the command may run */
        canActivate(
        command: CliProcessCommand,
        processor: ICliCommandProcessor,
        context: ICliExecutionContext,
        ): CliCommandGuardResult | Promise<CliCommandGuardResult>;
        }
      const ICliCommandGuard_TOKEN = 'cli-command-guard';

Return Values

canActivate returns Effect
true or nothing The command is allowed; the next guard runs
false Blocked with <command>: permission denied
a non-empty string Blocked; the string is printed as the error
{ allowed, message } Explicit form; message is printed when allowed is false
throws / rejects Blocked with <command>: blocked by guard '<name>' (<error>) (fails closed)

A blocked command prints the message as an error and exits with code -1.

Execution Order

  1. The input is parsed and the processor (or sub-processor) is resolved.
  2. Global parameters such as --help are handled. Help is never guarded.
  3. The positional value is extracted into command.value.
  4. Guards run, sorted by ascending priority. For each guard, appliesTo is evaluated first (if defined), then canActivate. The first guard that blocks stops the chain.
  5. Required values and parameters are validated, processor hooks run, then processCommand.

Accessing the Context

Both appliesTo and canActivate receive the execution context of the command about to run. A guard can use it to decide what should be guarded and whether it may run:

  • context.services.get(token) / getRequired(token) resolve any registered service, for example a policy, permission or feature-flag service from another module.
  • context.userSession gives the signed-in user and their groups, when a users module is loaded.
  • processor.metadata carries declarative flags such as requireAuth and requiredGroups.
  • command.value and command.args hold the parsed input.
  • context.reader can prompt the user, e.g. for a confirmation guard.

Return a message to report a denial rather than writing to the terminal yourself, so output stays consistent.

Registering Guards from a Module

Add guards to a module's guards array. When the module boots, each guard is registered as a multi-provider under ICliCommandGuard_TOKEN. Several modules can contribute guards and all of them run. 

import { ICliCommandGuard, ICliModule } from '@qodalis/cli-core';
        const maintenanceGuard: ICliCommandGuard = {
        name: 'maintenance',
        priority: -50,
        appliesTo: (processor) => processor.metadata?.module === 'billing',
        canActivate: (_command, processor, context) => {
        const status = context.services.get<MaintenanceStatus>(MaintenanceStatus_TOKEN);
        return status?.active
        ? `${processor.command}: billing is in maintenance until ${status.until}`
        : true;
        },
        };
        export const billingModule: ICliModule = {
        apiVersion: 2,
        name: 'billing',
        processors: [new InvoiceProcessor()],
        services: [{ provide: MaintenanceStatus_TOKEN, useValue: { active: false } }],
        guards: [maintenanceGuard],
      };

Guards can also be registered at runtime, for example from a module's onInit: 

context.services.set({ provide: ICliCommandGuard_TOKEN, useValue: myGuard, multi: true });

Example: Policy Resolved from a Service

The guard below asks a service which commands are behind a feature flag, and whether the current user may use them. 

const featureFlagGuard: ICliCommandGuard = {
        name: 'feature-flags',
        appliesTo: (processor, _command, context) =>
        context.services.get<FeatureFlags>(FeatureFlags_TOKEN)?.isFlagged(processor.command) ?? false,
        canActivate: async (_command, processor, context) => {
        const flags = context.services.getRequired<FeatureFlags>(FeatureFlags_TOKEN);
        const enabled = await flags.isEnabled(processor.command, context.userSession?.user);
        return enabled ? true : `${processor.command}: not available for your account`;
        },
      };

Processors declare access requirements in their metadata. Three guards built into the engine (access:require-auth, access:required-groups, access:required-permissions) enforce them as soon as an auth module registers an ICliAuthorizationService; until then the flags are informational. 

const deployProcessor: ICliCommandProcessor = {
        command: 'deploy',

        metadata: {
        requireAuth: true,                    // must be signed in
        requiredGroups: ['ops', 'release'],   // member of at least one
        requiredPermissions: ['deploy:run'],  // holds all of these

        async processCommand(command, context) { /* ... */ },
        };
        export const deployModule: ICliModule = {
        apiVersion: 2,
        name: 'deploy',
        processors: [deployProcessor],
        // Declared permissions appear in `perms --list` and can be granted to groups
        permissions: [{ name: 'deploy:run', description: 'Run deployments' }],

Checking Permissions in Code

The generic helpers in @qodalis/cli-core work with any auth module and allow everything when none is loaded: 

import { cliAuthorize, cliCanAccess, CliAccessDeniedError } from '@qodalis/cli-core';
        if (!cliAuthorize(context, 'deploy:rollback')) {
        throw new CliAccessDeniedError('deploy: rollback not permitted');  // printed as a plain error
        }
        // rwx check on a resource you own (files, records, ...)
      const allowed = cliCanAccess(context, { ownership: { uid: 'alice', gid: 'dev' }, permissions: 'rw-r-----' }, 'write');

Permissions are resource:action strings with * wildcards (deploy:*, *). The files module uses cliCanAccess for rwx checks on the virtual file system.

Client-side checks improve the experience but are not a security boundary. When commands call a server, the server must still authorize each request.
