The admin plugin serves the dashboard at /qcli/admin on the Node, .NET and Python servers: the same single-page app, in eleven languages, light or dark. It has a few pages of its own; every other page comes from the server plugin that owns its API, so a server shows a page only when it has the plugin. Below: how to set it up step by step, what each page does, and how to add pages of your own.

Set it up, step by step

1. Add the admin and users plugins

The admin plugin serves the dashboard; the users plugin gives it accounts, groups and permissions (without it, the admin plugin has one account of its own, set in its options). Mount the users plugin before the admin plugin signs anyone in, and point the admin plugin at it:

Node 
npm install @qodalis/cli-server-node @qodalis/cli-server-plugin-users @qodalis/cli-server-plugin-admin

import { createCliServer } from '@qodalis/cli-server-node';
import { CliUsersBuilder } from '@qodalis/cli-server-plugin-users';
import { CliAdminBuilder } from '@qodalis/cli-server-plugin-admin';

const cli = createCliServer({ configure: (builder) => builder });
const users = new CliUsersBuilder().build(cli.eventBus);
const admin = new CliAdminBuilder()
    .setAuthProvider(users.serverAuth)    // sign in with the users plugin's accounts
    .build({ registry: cli.registry, eventSocketManager: cli.eventSocketManager, builder: cli.builder, executor: cli.executor });
cli.mountPlugin(admin);
cli.mountPlugin(users);

const server = cli.app.listen(8047);
cli.eventSocketManager.attach(server);
.NET 
dotnet add package Qodalis.Cli.Plugin.Users
dotnet add package Qodalis.Cli.Plugin.Admin

builder.Services.AddControllers().AddCli(cli =>
{
    cli.AddUsers();
    cli.AddAdmin();
});

var app = builder.Build();
app.UseWebSockets();
app.UseQodalisUsers();
app.UseQodalisAdmin();
app.MapControllers();
app.UseCli();
Python 
pip install qodalis-cli-server qodalis-cli-server-plugin-users qodalis-cli-server-plugin-admin

from qodalis_cli import CliServerOptions, create_cli_server
from qodalis_cli_users import CliUsersBuilder
from qodalis_cli_admin import CliAdminBuilder, AdminBuildDeps

result = create_cli_server(CliServerOptions())
users_plugin = CliUsersBuilder().build()
result.mount_plugin(users_plugin)
admin_plugin = CliAdminBuilder().set_users_plugin(users_plugin).build(AdminBuildDeps(
    registry=result.registry, event_socket_manager=result.event_socket_manager, builder=result.builder,
))
result.mount_plugin(admin_plugin)
# Start the users plugin with the app: await users_plugin.startup() in its lifespan

2. Sign in and set your own password

Open http://your-server/qcli/admin and sign in as root. Its first password is the users plugin's default (set it with setDefaultAdminPassword / DefaultAdminPassword / set_default_admin_password); change it before the server is reachable from other devices, on the Account page. A user whose password an administrator set is asked for a new one right after signing in, before the dashboard opens:

When your own application signs users in (the users plugin with an auth adapter), the dashboard has no password form: it sends people to your sign-in page and takes the token you hand back (#token=). Set the address with the admin plugin's signInUrl.

3. Add the pages you need

Each page comes with its plugin: add the plugin and its page appears in the sidebar, for the users allowed to open it. Nothing else to install: the page's build is embedded in the plugin's package.

Databases

Each database with its size, load and largest tables, and its migrations, applied or rolled back from the page.

Node: @qodalis/cli-server-plugin-databases 
const databases = new CliDatabasesBuilder()
    .addDatabase('main', { connection: postgresConnection(pool), applyOnStartup: true })
    .addSqlFolder('main', './migrations')
    .build();
await databases.applyOnStartup();
cli.mountPlugin(databases);
.NET: Qodalis.Cli.Plugin.Databases 
cli.AddDatabases(d => d
    .AddDatabase("main", db => db
        .UseConnection(_ => new NpgsqlConnection(connectionString))
        .ApplyMigrationsOnStartup())
    .AddSqlFolder("main", "./migrations"));
Python: qodalis-cli-server-plugin-databases 
databases = (
    CliDatabasesBuilder()
    .add_database("main", CliMigrationDatabaseOptions(postgres_connection(pool), apply_on_startup=True))
    .add_sql_folder("main", "./migrations")
    .build()
)
await databases.apply_on_startup()   # in the app's lifespan
result.mount_plugin(databases)

Files and data explorer

These two come with the server itself: enable the filesystem, or add a data explorer source.

Node 
createCliServer({ configure: (builder) => builder
    .addFileSystem({ allowedPaths: ['/srv/files'] })
    .addDataExplorerProvider(new SqlDataExplorerProvider({ type: 'sqlite', filename: './app.db' }), { name: 'app' }) });
.NET 
cli.AddFileSystem(o => o.UseOsFileSystem(os => os.AllowedPaths = ["/srv/files"]));
cli.AddDataExplorerSql("Data Source=app.db", o => o.Name = "app");
Python 
def configure(builder):
    builder.add_filesystem(FileSystemOptions(allowed_paths=["/srv/files"])) \
        .add_data_explorer_provider(SqlDataExplorerProvider("./app.db"), DataExplorerProviderOptions(name="app"))

Plugins also add cards to the Overview and items to its Needs attention list: Jobs its runs of the last 24 hours and failing jobs, Databases pending or failed migrations.

4. Give people access

On the Users page, create the accounts and put them in groups. A group holds permissions, and a user holds those of all their groups. To open the dashboard a user needs admin:access; each page needs its own (see the table below). Wildcards work: jobs:* is every jobs permission, * everything. A first password is temporary by default: the user picks their own at the first sign-in.

Where your application manages the users (read-only users and groups) or signs them in, the Users page only shows them: no forms to change them.

5. Each user's own account

Every signed-in user has an Account page in the account menu: their profile and email, their password, and what they may do. When your application signs users in, the password is changed there instead.

A plugin's page is a module built in the dashboard's repository (@qodalis/cli-dashboard-module-<name>) and embedded in the plugin's package; the server serves its files at /qcli/modules/<id>. To serve another build of a page, or leave it out:

Node 
new CliUsersBuilder().setUsersDashboardDir(false)   // no Users and Account pages
cli.builder.setDashboardModuleDir('filesystem', './my-filesystem-build')
.NET 
cli.ConfigureDashboardModule("users", null);          // no Users and Account pages
cli.ConfigureDashboardModule("filesystem", new PhysicalFileProvider("/srv/my-filesystem-build"));
Python 
CliUsersBuilder().set_users_dashboard_dir(False)      # no Users and Account pages
CliServerOptions(dashboard_pages={"filesystem": "./my-filesystem-build"})

Colors, name and icon are set in the admin plugin's options (see Color scheme).

Your own pages

A plugin of yours (or the host application) adds pages the same way: it registers a dashboard extension and serves an ES module. The dashboard lists the extension in its navigation, for users holding its permission, and at /x/<id> loads the module and mounts it with its context: the signed-in user and permissions, the theme, the language, routing below /x/<id>, notices, a confirm dialog, server events and fetch with the dashboard's session.

1. Register the page

Node 
cli.builder.addDashboardExtension({
    id: 'billing', title: 'Billing', titles: { de: 'Abrechnung' }, icon: '💳',
    group: 'data', order: 30, permission: 'billing:read',
    entry: '/billing/admin/extension.js', styles: ['/billing/admin/extension.css'],
});
.NET 
cli.AddDashboardExtension(new CliDashboardExtension
{
    Id = "billing", Title = "Billing", Icon = "💳", Group = "data", Permission = "billing:read",
    Entry = "/billing/admin/extension.js", Styles = ["/billing/admin/extension.css"],
});
Python 
builder.add_dashboard_extension({
    "id": "billing", "title": "Billing", "icon": "💳", "group": "data", "permission": "billing:read",
    "entry": "/billing/admin/extension.js", "styles": ["/billing/admin/extension.css"],
})
Field Meaning
idLower case letters, digits and dashes; the page is at /x/<id>.
title, titlesThe title, and its translations by language code.
iconA character or an image URL.
groupThe sidebar section: overview, operations, data, access or system (the default). account lists the page in the account menu instead of the sidebar.
orderIts place in the section (default 100).
permissionOnly users holding it see the page (wildcards match).
entry, stylesThe ES module and its stylesheets.
widgetsoverview: the module adds cards and attention items to the Overview; palette: entries in the command palette.
searchWhere the page searches, e.g. /?q=: the command palette offers "Search Billing for …".

2. Build the page with the kit

@qodalis/cli-server-dashboard-kit holds the dashboard's components, theme (a Tailwind preset), the texts of its components in eleven languages and the extension API, so a page looks and behaves like the dashboard's own.

Install 
npm install @qodalis/cli-server-dashboard-kit react react-dom
npm install -D vite @vitejs/plugin-react tailwindcss@3 postcss autoprefixer
src/index.tsx 
import { PageHeader, StatCard, defineExtension, defineMessages, useApi, useAsync, useTranslations } from '@qodalis/cli-server-dashboard-kit';

const messages = {
    billing: defineMessages({
        en: { title: 'Billing', open: 'Open invoices' },
        de: { title: 'Abrechnung', open: 'Offene Rechnungen' },
    }),
};

function Billing() {
    const api = useApi();                       // JSON with the dashboard's session
    const { t } = useTranslations(messages);    // the dashboard's language
    const { data } = useAsync(() => api.get<{ open: number }>('/api/billing/stats'), [api]);
    return <PageHeader title={t('billing.title')} subtitle={`${data?.open ?? '…'}`} />;
}

function OpenInvoices() {
    const { t } = useTranslations(messages);
    return <StatCard label={t('billing.open')} value={3} />;
}

export default defineExtension(Billing, {
    // With widgets: ["overview", "palette"] in the registration
    overview: {
        cards: [{ id: 'open', size: 'stat', component: OpenInvoices }],   // stat, half or full
        attention: async () => [{ id: 'late', level: 'warning', title: '3 invoices late', path: '/?status=late' }],
    },
    palette: async () => [{ id: 'inv-42', label: 'Invoice 42', path: '/42' }],
});

3. Build it and serve the files

vite.config.ts 
export default defineConfig({
    plugins: [react()],
    define: { 'process.env.NODE_ENV': JSON.stringify('production') },
    build: { lib: { entry: 'src/index.tsx', formats: ['es'], fileName: () => 'extension.js', cssFileName: 'extension' } },
});

vite build writes dist/extension.js and dist/extension.css; serve both at the entry and styles you registered (React and the kit are bundled in). Pages of a server plugin can use the servers' helpers, which serve a build with versioned URLs and register it: Node dashboardModulePage(dir, info) in the plugin's dashboardPages, .NET cli.AddDashboardModule(module, fileProvider), Python dashboard_module_page(dir, prefix, extension).

The kit also has the dashboard's hooks (useQueryParams, usePaging, useStoredState, useLiveReload on server events), charts, and test helpers at @qodalis/cli-server-dashboard-kit/testing to mount a page with a fake context and server. The full contract between server, dashboard and page is in docs/extensions.md, and the kit's guide in its README.
